# Script-isolation check

Checks, in the real app and its real webview, that a dictionary's JavaScript can't reach the Tauri backend (issue #12). Rerun it after upgrading Tauri, wry or WebView2, and after any change to how article frames are built.

The probe is the `scripts` fixture (`src-tauri/tests/fixtures/scripts/`, generated by `tools/make-fixtures`):

- an inline script, `probe.js` from the `.mdd` and `loose.js` beside the `.mdx` each mark the page when they run;
- `probe.js` also tries every route out of the frame: the parent window, `top`, popups, the IPC custom protocol, the `invoke` Tauri injects into frames (with and without its `fetch` transport, which forces the `postMessage` fallback carrying the real invoke key), and raw `chrome.webview.postMessage`.

Every route that could change something calls `add_file` with a marker path (`ultra-dict-ipc-probe-<route>.mdx`). The library records even a missing file, so a marker in the library database means a dictionary script reached the backend.

## Running it (Windows)

1. Start the app on a throwaway library, with the DevTools port open. The environment variable **replaces** the window's `additionalBrowserArgs` from `tauri.conf.json`, so repeat them in full:

   ```sh
   ULTRA_DICT_LIBRARY=/tmp/iso/library.sqlite3 \
   WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection,IsolateSandboxedIframes --remote-debugging-port=9223" \
   bun run tauri dev
   ```

2. Once the window is up, from the repository root:

   ```sh
   bun tools/isolation-check/check.ts /tmp/iso/library.sqlite3 9223
   ```

It adds the fixture, opens `probe` with scripts off, ticks "Allow scripts", and prints what ran, what the probe could reach, and whether any marker reached the library. It exits 0 and ends with `RESULT: isolated` only if:

- scripts off: nothing ran;
- scripts on: all three scripts ran, the frame's origin is opaque and the app can't read its document;
- no marker is in the library.

If the scripts-on scripts didn't run, the app was probably started without `IsolateSandboxedIframes` disabled (see "Why that flag" below).

## Why that flag

Chromium (WebView2 included) gives sandboxed iframes their own renderer process. WebView2 doesn't yet route a new frame process's first requests through the app's custom schemes, so a scripted frame's `<script src>`, stylesheets and images, all served over `dict`, fail to load with `net::ERR_CONNECTION_REFUSED`. Disabling `IsolateSandboxedIframes` keeps the frame in the app's renderer process. The frame's origin stays opaque, so the browser still keeps it from reaching the app.
